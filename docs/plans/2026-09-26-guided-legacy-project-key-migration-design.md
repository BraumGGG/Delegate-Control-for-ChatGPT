# 旧 Project Key 引导迁移设计说明

## 背景与目标

历史版本会为项目生成 `new-project`、`new-project-2` 等通用 key。它们可以路由，但不能表达项目身份。目标是在不自动修改身份的前提下，识别这些旧 key，为 Realize 和 DCFC 提供清晰、可延期、需要确认的迁移流程，并复用现有安全迁移命令。

## 现状与约束

- 固定 11 工具、单 Tunnel、单 Proxy、固定 Router 架构不变。
- 已有 `migrate_project_key` Tauri 命令负责停机检查、校验、设置原子写入、日志目录迁移和失败回滚。
- 普通 Project Name 编辑不得改变已建立的 key。
- 不自动迁移，不把任意自定义 key 误判为旧 key。
- 外部提示词、复制的工具调用和第三方文档无法自动更新。

## 方案对比

### 方案一：启动时弹出全局模态框

- 优点：曝光强。
- 缺点：打断启动，多个项目处理顺序僵硬，容易被误解为强制迁移。

### 方案二：项目行内引导卡片（采用）

- 优点：当前项目、旧 key、建议 key 和操作处于同一上下文；可逐个延期；可复用现有迁移面板。
- 缺点：项目较多时页面会变长。

### 方案三：只在“更改 key”按钮旁显示徽标

- 优点：改动小。
- 缺点：信息不足，无法直接解释旧 key 与建议迁移，也不满足直接审阅要求。

## 推荐方案

采用项目行内引导卡片。仅当 key 匹配 `new-project` 或 `new-project-N` 时显示。建议 key 由当前 Project Name 规范化得到；Realize 建议 `realize`，DCFC 建议 `dcfc`。若目标冲突，仍展示建议值和冲突原因，但禁止确认，要求用户改用现有迁移输入框处理。

## 详细设计

### 架构

- `src/projectIdentity.ts`：Project Key 规范化、旧 key 检测、迁移建议与冲突判断。
- `src/App.tsx`：行内引导、会话级延期状态、迁移面板 old→new 预览、即时校验和成功反馈。
- Rust 后端继续作为迁移安全边界，不新增绕过路径。

### 数据流

1. 加载设置后，对每个已保存项目执行旧 key 检测。
2. 未延期的旧项目显示当前 key、建议 key 和说明。
3. “稍后处理”仅在当前应用会话隐藏该项目引导，下次启动重新提醒。
4. “开始迁移”打开现有迁移面板并预填建议 key。
5. 前端先校验格式与重复，确认后调用 `migrate_project_key`。
6. 后端成功返回新设置后，旧 key 引导自然消失，并显示明确成功消息。

### 异常与边界

- `screencast` 等自定义 key 不显示引导。
- 非法建议或重复目标在确认前显示原因并禁用确认。
- 运行中或存在未保存设置时不能开始迁移。
- 取消关闭面板且不修改身份。
- 日志目录冲突和持久化失败由后端返回，原身份保持可用。

### 测试策略

- Node/TypeScript 单元测试：旧 key 检测、名称建议、冲突、非拉丁回退。
- Rust 单元测试：迁移成功、目标冲突、日志目录迁移和回滚。
- Playwright 交互检查：引导显示、延期、取消、重复 key、名称与 key 分离、Realize/DCFC 成功迁移、窄窗口布局。
- Release 构建后更新本机安装，保留旧二进制备份。

## 风险与待确认项

- “稍后处理”为会话级状态，不持久化；这是为了避免用户永久错过身份清理提醒。
- 实际本机 Realize/DCFC 身份不会在安装时静默迁移，必须由用户在新 UI 中逐项确认。
