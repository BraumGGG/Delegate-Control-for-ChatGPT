# 已有文本文件编辑能力设计说明

## 背景与目标

当前 `chatgpt-delegate` 主要提供 Markdown 报告和任务结果的保存、列出及读取能力，不支持对已有文件进行追加、精确修改或删除片段。用户希望 ChatGPT 能在当前项目目录内继续编辑已有文档，同时保持 DCFC 的多项目同时在线、单 Tunnel、项目目录隔离和现有 Connector 兼容性。

本功能的目标是：

- 支持项目目录内 UTF-8 纯文本文件的读取、追加、精确替换和精确删除；
- 保留现有 7 个 Connector 工具及其行为，不破坏旧会话；
- 严格限制路径在当前项目输出目录内；
- 防止误覆盖、误删除和并发修改导致的数据丢失；
- 不新增 Tunnel ID，不改变多项目聚合拓扑。

## 现状与约束

- DCFC 为每个项目启动一个独立 `chatgpt-delegate` 进程，并通过一个共享 `mcp-proxy` 和一个 `tunnel-client` 聚合到 ChatGPT。
- 上游 `--output-dir` 在进程启动时固定，因此每个项目的文件编辑边界由该项目的输出目录决定。
- 当前上游 MCP 工具包括 `connector_status`、`list_reports`、`read_report`、`save_markdown_report`、`list_results`、`read_result`、`save_task_result`。
- 旧 Connector 会话可能缓存工具列表；新增工具后需要重启连接或重新连接才能发现新工具，但旧工具必须继续可用。
- 不读取、输出或提交 Runtime API Key，不提交本机设置、日志、构建产物或测试 evidence。

## 方案对比

### 方案一：扩展 `chatgpt-delegate`（推荐）

在现有 Connector 内增加文件编辑工具，并以兼容版本替换当前可执行文件。每个项目仍只运行一个 Delegate 进程。

- 优点：不增加每项目进程；复用现有 `--output-dir` 隔离；工具发现和项目 namespace 逻辑保持一致；对用户使用方式最自然。
- 缺点：需要维护上游兼容改动；上游升级时需要重新合并；需要提供新的 Windows 可执行文件。

### 方案二：增加独立文件编辑 MCP

保留上游 Connector 不变，为每个项目启动一个轻量文件编辑 MCP，再由共享 `mcp-proxy` 聚合。

- 优点：不修改上游；安全策略由 DCFC 完全控制；上游升级风险较低。
- 缺点：每个项目增加一个进程；Proxy 配置、进程清理和工具 namespace 更复杂；更容易扩大现有运行时故障面。

### 方案三：只提供整文件读取和重写

增加 `read_text_file` 与 `write_text_file`，由 ChatGPT 读取全文后写回。

- 优点：实现简单。
- 缺点：容易因一次错误调用覆盖整个文件；无法可靠表达局部修改；不作为正式方案。

## 推荐方案

采用方案一，并将编辑能力作为现有 Connector 的增量扩展。保留全部旧工具，新增以下工具：

```text
read_text_file
append_text_file
replace_text_in_file
delete_text_from_file
```

第一版不提供无条件整文件覆盖工具，避免错误调用清空用户文档。若后续确有需求，再单独设计带版本校验的完整写入操作。

## 详细设计

### 架构

每个项目的 `chatgpt-delegate` 进程同时提供旧报告/结果工具和新增文本编辑工具。DCFC 不新增 Tunnel；共享固定 Router MCP 对外只注册一套固定工具名，项目通过可选 `project_id` 参数路由。

单项目和多项目都使用相同的裸工具名。新增工具也不拼接项目 namespace，例如始终使用 `append_text_file`。项目数量、名称和 ID 变化不会改变 ChatGPT 侧的工具 Schema。

### 文件范围与路径校验

- 文件参数只能是相对于当前项目输出目录的文件名或相对路径；拒绝盘符、UNC 路径、绝对路径和包含 `..` 的路径。
- 解析后的路径必须位于项目根目录下；使用规范化路径检查，避免符号链接或路径分隔符绕过。
- 只接受 UTF-8 纯文本文件；第一版允许常见文本扩展名和无扩展名文本，拒绝明显二进制内容。
- 单文件读取和写入继续受最大字节数限制，限制值沿用 Connector 的 `max_bytes` 配置。
- 不允许访问项目输出目录之外的文件，也不允许执行命令或调用外部 API。

### 工具语义

#### `read_text_file`

参数：`filename`、可选 `start_line`、可选 `max_bytes`。

返回：规范化文件名、绝对路径展示值、内容、字节数、内容指纹和最后修改时间。文件不存在或编码无效时返回可理解错误。

#### `append_text_file`

参数：`filename`、`content`、可选 `expected_sha256`。

将内容追加到文件末尾。必要时只补一个换行，避免新内容与原末尾文本粘连。文件不存在时默认拒绝创建，除非后续明确扩展为创建模式。

#### `replace_text_in_file`

参数：`filename`、`old_text`、`new_text`、可选 `expected_occurrences`、可选 `expected_sha256`。

默认要求 `old_text` 在文件中恰好出现一次；出现零次或多次都拒绝执行。支持调用方显式声明预期出现次数，但仍需与实际一致。写入前检查内容指纹，文件已被其他程序修改时拒绝覆盖。

#### `delete_text_from_file`

参数：`filename`、`text`、可选 `expected_occurrences`、可选 `expected_sha256`。

语义与精确替换相同，只是将匹配文本替换为空字符串。默认只允许唯一匹配，避免误删多处内容。

### 写入与恢复

- 所有修改先读取并校验原文件，再写入同目录临时文件。
- 临时文件成功写入并 flush 后执行原子替换。
- 原文件替换前生成受控备份，备份位于当前项目目录下的隐藏/保留子目录，且不进入报告列表。
- 任何校验失败、编码失败或写入失败都保留原文件。
- 返回修改前后字节数、内容指纹和实际操作摘要，便于 ChatGPT 和 Codex 继续工作。

### 并发和冲突处理

- `expected_sha256` 可由 ChatGPT 在读取后带回，避免覆盖 Codex 或用户刚刚保存的修改。
- 没有提供指纹时，仍执行精确文本匹配；但对于替换和删除，如果文件在读取期间发生修改，则再次读取并重新校验，发现变化即拒绝。
- 不做静默合并，不覆盖未知来源的并发修改。

### 错误处理与兼容

- 新工具错误以 MCP 工具错误返回，包含失败原因和建议动作，不暴露 Runtime API Key。
- 旧工具的文件命名、报告头信息、结果目录结构和返回字段保持不变。
- DCFC 启动时检查 Connector 版本或工具能力；发现旧可执行文件时，现有功能仍可用，但界面明确提示“文件编辑工具不可用”，不伪造已启用。
- 替换 Connector 可执行文件需要重启 DCFC 管理的项目 MCP、Proxy 和 Tunnel；界面明确显示重启要求。

## UI 与用户流程

- 设置页显示当前 Connector 版本能力：报告读写、文本编辑是否可用。
- 项目当前目录和生效状态继续在总览及设置页显示。
- 用户在 ChatGPT 中用自然语言提出“读取、追加、替换、删除”请求；ChatGPT 选择对应工具。
- 请求未明确项目时，单项目可使用 DCFC 当前项目；多项目且没有当前项目时必须先澄清，不得猜测目录。工具名始终保持固定。
- 目录或 Connector 变更后，UI 明确提示停止并重新连接。

## 测试策略

### 单元测试

- 相对路径、绝对路径、UNC 路径、`..` 和符号链接逃逸校验；
- UTF-8 文本读取和二进制/非法编码拒绝；
- 追加换行行为；
- 唯一匹配、零匹配、多匹配错误；
- 替换和删除的内容指纹冲突；
- 原子写入失败时原文件保持不变；
- 最大字节数限制；
- 多项目路径互斥和固定 Router 工具目录。

### 集成测试

- 新旧 7 个工具均可注册并调用；
- 单项目与多项目都使用固定裸工具名，并通过 `project_id` 路由；
- 多个项目同时在线时文件只能落入各自目录；
- 重启 DCFC 后目录和工具能力状态恢复；
- Connector 旧版本运行时不影响旧功能，并给出能力提示。

### 桌面端自动化

使用 `clienttrail-desktop-testing` skill 进行结构化检查：

- 冷启动、连接重启和工具能力提示；
- 项目目录显示和切换提示；
- 编辑能力不可用时的明确状态；
- 最小窗口尺寸下无布局重叠；
- Runtime API Key 不出现在 DOM、日志、测试报告或 Git diff。

## 风险与待确认项

- 上游 Connector 的 Windows 发布方式需要固定版本并记录构建来源；
- 如果上游未来改变 FastMCP 注册方式，需要重新验证工具名和返回结构；
- 是否允许“文件不存在时 append 自动创建”留待实现阶段根据用户工作流决定，第一版默认拒绝，避免拼写错误创建错误文件；
- 备份保留数量和清理策略应在实施计划中确定，不能让备份文件污染现有报告列表。
